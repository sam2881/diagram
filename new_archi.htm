⚠️ 2. Problem Statement

The Challenge: Alert Fatigue & Manual Toil

Modern enterprises face an overwhelming volume of IT incidents and data pipeline requests. Traditional approaches suffer from several critical limitations:

❌ Current Pain Points

  • Alert Fatigue: Teams receive 1000s of alerts daily, 90%+ are noise
  • Slow Resolution: Average MTTR is hours to days for routine issues
  • Knowledge Silos: Remediation knowledge trapped in individual heads
  • Manual Pipelines: Data engineers spend 60% of time on boilerplate code
  • Inconsistent Quality: Pipeline code varies widely in style and security
  • Audit Gaps: Hard to track who did what and why
  • Scaling Issues: Can't hire fast enough to match infrastructure growth

✓ How We Solve It

  • AIOps Correlation: 94% noise reduction through intelligent deduplication
  • Swarm RAG: 4 AI agents find best remediation from knowledge base
  • Chain-of-Thought: LLM reasons through problems step-by-step
  • Template Generation: Jinja2 templates ensure consistent, secure code
  • Automated Validation: Built-in linting, schema checks, security scans
  • Kafka Event Spine: Every action is an immutable, auditable event
  • Human-in-the-Loop: AI augments humans, doesn't replace judgment
⚡ Why Not Just Use ChatGPT/Copilot?

Generic AI tools lack enterprise controls. They can't enforce approval gates, maintain audit trails, integrate with your ITSM tools, or guarantee consistent output formats. This platform provides governed AI that fits into existing workflows while maintaining compliance requirements.

⚡ 4. FAST Multi-Agent Architecture

FAST = Federated Agents with Strict Transitions. A production-grade multi-agent system where 9 specialized agents operate under a Governor orchestrator with a 24-state distributed state machine. Parallel where safe, strict sequence where required.

Architecture Principle

This system behaves like a senior on-call SRE, not a script runner. No blind execution, no unverified resolution, no irreversible action without rollback, no action without audit, no learning without feedback.

⚙️ 5. Platform Components Explained

The platform includes three horizontal layers that provide cross-cutting capabilities across all workflows. These components ensure security, reliability, and operational visibility for the entire system.

🟢 PLATFORM SERVICES

Infrastructure services that support all workflows

Component How We Use It
Schema Registry Confluent Schema Registry validates all Kafka event payloads against Avro/JSON schemas before publishing. This ensures backward compatibility when event structures evolve and prevents malformed data from entering the system. Every topic (incident.*, pipeline.*) has registered schemas with versioning.
State Store Redis stores LangGraph workflow state, enabling pause/resume capabilities and crash recovery. When a workflow waits for human approval, state is persisted so the system can resume exactly where it left off. Also used for caching LLM responses and session management.
Vault/KMS GCP Secret Manager stores all sensitive credentials (API keys for Claude/OpenAI, ServiceNow passwords, database credentials). Secrets are injected into pods via Workload Identity - no hardcoded credentials anywhere. Automatic rotation every 90 days for external API keys.
Feature Flags LaunchDarkly/GCP Feature Flags control which LLM model is used, enable/disable specific agents, and manage gradual rollouts. Example: We can instantly switch from Claude to GPT-4 if one provider has issues, without redeploying code. Also used to enable experimental features for specific users.
OIDC/SPIFFE SPIFFE provides cryptographic identities for every service, enabling mutual TLS (mTLS) between components. No service can communicate without valid SPIFFE identity - prevents lateral movement if one component is compromised. OIDC handles human authentication via Google Cloud Identity or corporate IdP.
Service Mesh Istio/Anthos Service Mesh manages all service-to-service communication with automatic retries, timeouts, and load balancing. Provides traffic shifting for canary deployments (route 5% traffic to new version, monitor, then increase). Also enforces network policies - only allowed services can communicate.
SLO Engine Tracks Service Level Objectives and triggers alerts when error budgets are being consumed too fast. Example: If "incident triage < 2 minutes" SLO drops below 99%, PagerDuty alert fires before customers notice. Dashboards show real-time SLO compliance for all critical paths.
Cost Controls Monitors and enforces spending limits on LLM API calls (Claude, OpenAI), GCP resources, and external services. Alerts when daily LLM spend exceeds thresholds. Auto-scales down non-critical workloads during cost spikes. Monthly budget allocation per team/project with automated reports.

🟣 AI GUARDRAILS

Security and safety controls for all LLM interactions

Guardrail How We Use It
Prompt Injection Detects and blocks attempts to manipulate LLM behavior through malicious input in incident descriptions or pipeline requests. Uses pattern matching for known attacks + a classifier model that scores input risk. Example: Blocks "ignore previous instructions and..." patterns before they reach the LLM.
PII Redaction Microsoft Presidio scans all text before sending to LLM and masks sensitive data (SSN, credit cards, emails, phone numbers). Redacted values are replaced with tokens like [EMAIL_1] that can be restored in output if needed. Prevents accidental exposure of customer PII in LLM logs or responses.
Output Validation Every LLM response is validated against expected JSON schemas before being processed. If remediation plan doesn't match required structure (steps, risk_level, confidence), it's rejected and retried. Prevents malformed outputs from causing downstream failures or executing unexpected actions.
Jailbreak Block Maintains database of known jailbreak patterns and prompt manipulation techniques. Blocks requests that attempt to make LLM ignore safety guidelines or role-play as unrestricted AI. Regular updates from security research to catch new jailbreak methods.
Content Safety Filters LLM outputs for harmful, violent, or inappropriate content before displaying to users. Even if LLM somehow generates unsafe content, this layer prevents it from reaching the UI. Logs all filtered content for security review and model improvement.
Hallucination Check Verifies LLM claims against RAG source documents to detect fabricated information. If remediation steps reference non-existent runbooks or made-up commands, confidence score drops. Items with confidence < 0.7 are flagged for human review before approval.
LLM-as-Judge A different LLM model (e.g., Claude Haiku) evaluates outputs from the primary model (e.g., Claude Sonnet). Using different models prevents confirmation bias - the judge doesn't share the same blind spots. Scores quality, safety, and appropriateness; gates whether output proceeds to human approval.

🔵 OBSERVABILITY

Monitoring, logging, and debugging capabilities

Component How We Use It
Structured Logs All components emit JSON-formatted logs with correlation_id linking related events across services. When investigating an incident, search by correlation_id to see complete flow from MCP → Kafka → LangGraph → execution. Logs include timing, input/output summaries (PII-redacted), and error details.
OpenTelemetry Distributed tracing shows exact path and timing of requests through the system. Each Kafka event, LLM call, and database query is a span in the trace - visualized as waterfall diagrams. Critical for debugging slow requests: instantly see if delay is in RAG search, LLM response, or approval wait.
Prometheus Collects time-series metrics from all services: request rates, error rates, latencies, queue depths. Powers Grafana dashboards showing real-time system health and historical trends. Alerting rules fire PagerDuty alerts when metrics exceed thresholds (e.g., error rate > 1%).
LangSmith LangChain's observability platform specifically for LLM debugging - captures every prompt, response, and token usage. When LLM produces unexpected output, LangSmith shows exact prompt that was sent and full response received. Also tracks cost per LLM call and helps optimize prompts for better performance/cost ratio.
LangGraph Studio Visual debugger for LangGraph workflows - shows state machine transitions in real-time. See exactly which node is active, what's in the state, and why a particular edge was taken. Invaluable for debugging complex multi-agent workflows and understanding decision paths.
Circuit Breakers Monitors external dependency health (LLM APIs, ServiceNow, Jira) and "trips" when failures exceed threshold. When circuit is OPEN, requests fail fast instead of waiting for timeout - prevents cascade failures. Auto-recovers after 30 seconds (HALF-OPEN state tests with single request before fully closing).
💡 How These Layers Work Together

When an incident arrives: Schema Registry validates the event format → Prompt Injection scans the description → PII Redaction masks sensitive data → LLM generates plan → Output Validation checks structure → LLM-as-Judge scores quality → LangSmith logs the interaction → Prometheus records metrics → Circuit Breaker monitors for failures. All protected by SPIFFE mTLS and tracked in State Store.

⚡ 11. Error Handling & Recovery

Error Categories & Responses

Error Type Example System Response Recovery
LLM Timeout Claude API > 30s Circuit breaker opens, fallback to GPT-4 Automatic retry with backoff
LLM Hallucination Confidence < 0.7 Judge rejects, marks for human review Human escalation
Kafka Unavailable Broker connection lost Buffer to local disk, alert fired Auto-replay when recovered
Execution Failure Terraform apply fails Publish pipeline.failed, halt workflow Human investigates, retrigger
Validation Error Generated code fails lint Return to Generator with feedback Max 3 retries, then human
External API Down ServiceNow 503 Circuit breaker, exponential backoff 5 fails → 30s open → retry

Dead Letter Queue (DLQ) Processing

DLQ Topics
  • incident.dlq - Failed incident processing
  • pipeline.dlq - Failed pipeline processing
  • remediation.dlq - Failed execution attempts

Policy: DLQ messages are retained for 7 days. Alert fires if DLQ depth > 10. On-call engineer reviews and either retriggers or marks as won't-fix with reason.

📖 14. Glossary

A2A (Agent-to-Agent)
Protocol for real-time communication between AI agents, used for swarm coordination and voting.
Chain-of-Thought (CoT)
AI reasoning pattern where LLM thinks step-by-step before providing an answer, improving accuracy.
CQRS
Command Query Responsibility Segregation - pattern where writes go to Kafka, reads come from database.
DLQ (Dead Letter Queue)
Kafka topic where failed messages are sent for later investigation and reprocessing.
Event Sourcing
Pattern where all state changes are stored as immutable events, enabling full replay capability.
HITL (Human-in-the-Loop)
Design pattern requiring human approval before AI-generated actions are executed.
Hub-and-Spoke
Architecture pattern where central orchestrator (hub) routes events to appropriate workflows (spokes).
LangGraph
Framework for building stateful, multi-agent AI workflows with explicit state machines.
MCP (Model Context Protocol)
Protocol for AI agents to invoke external tools via JSON-RPC 2.0, standardizing tool integration.
RAG (Retrieval Augmented Generation)
Technique combining vector search with LLM generation to ground responses in factual data.
ReAct Pattern
AI pattern where LLM controls execution loop - explicitly NOT used in this platform due to unpredictability.
Self-Reflection
AI pattern where a different LLM evaluates the output of another, avoiding confirmation bias.
StateGraph
LangGraph's state machine that controls workflow flow deterministically (not the LLM).
Swarm Intelligence
Pattern where multiple AI agents work together and vote/consensus on best answer.

python -m venv venv source venv/bin/activate pip install -r requirements.txt cp .env.example .env # Edit with your API keys

docker-compose up -d # Wait for services to be healthy docker-compose ps
