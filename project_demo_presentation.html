Why this project exists

Two functions burn engineering effort — and produce no differentiated value

Both are pattern-heavy and judgement-light in the majority of cases, yet both are executed as bespoke, manual work.

⚠ L1 Support · ITSM · Platform Operations
Alert fatigue
Thousands of alerts daily, 90%+ noise — real incidents are missed inside the noise floor
Slow resolution
MTTR in hours or days for routine issues → SLA breaches, overtime cost
Knowledge silos
Remediation know-how lives in individual engineers' heads — bus-factor risk, months to onboard
Manual toil
Triage → search the wiki → ask for approval on chat → run a script → write the ticket up by hand
📊 Data Engineering
Boilerplate dominates
Engineers spend ~60% of their time hand-writing ingestion, transforms, validation and DAGs
Inconsistent quality
The same pattern re-implemented per feed with slight, undocumented variations
Backlog of unmet demand
Every new feed is a project; analytics requests queue behind engineering capacity
Legacy migration debt
SSIS, COBOL and mainframe estates that nobody wants to touch by hand
⚖️ And underneath both — the audit problem
Hard to reconstruct who did what, why, and on whose authority. That is direct compliance exposure under SOC 2, ISO 42001, the EU AI Act and GDPR. Meanwhile headcount cannot grow as fast as infrastructure, so toil grows superlinearly with estate size.
❌ Why a generic AI assistant does not solve this
Off-the-shelf copilots cannot enforce approval gates, cannot keep a tamper-evident audit trail, cannot act inside ITSM workflows, and cannot guarantee output structure. Governance — not model quality — is the binding constraint.

The solution

Agentic AI, wrapped in an enterprise governance layer

Google Cloud supplies the runtime. The architecture supplies the control.

📜
1 · The event log is the system of record
Every state change is an immutable Pub/Sub message. Any incident or pipeline can be replayed from a snapshot. Durability, decoupling and a compliance-grade audit trail from one mechanism.
🧠
2 · A state machine controls flow — the LLM never does
The Agentspace Agent Graph decides which node runs next. LLM nodes only reason; code nodes only execute. ReAct is explicitly forbidden.
🔍
3 · Retrieval beats recall
Four retrieval agents — vector, keyword, graph, metadata — search in parallel and fuse by Reciprocal Rank Fusion, then a cross-encoder reranks. No single method is trusted alone.
⚖️
4 · Two independent validators before every action
Gemini Flash judges Gemini Pro's plan on quality, safety, factuality, feasibility and risk. Then a human approves. High-risk and production changes always require a person.
↻
5 · The system only learns from success
Verified successful resolutions are indexed back into the knowledge base. Failures are never indexed, so a bad pattern cannot be reinforced.
Where Google Cloud fits
Agentspace — managed agent graph + 100+ enterprise connectors Gemini 2.0 Pro — planning Gemini 2.0 Flash — independent judging Vertex AI Search — grounded retrieval Pub/Sub — event spine Cloud Composer + Dataproc — pipeline execution Cloud Build — governed execution Cloud DLP · KMS · Secret Manager — data protection
✓ Portable by design
Pub/Sub ↔ Kafka  |  Agentspace ↔ LangGraph  |  Gemini ↔ Claude/GPT  |  Vertex AI Search ↔ Weaviate. Same architecture, different managed services — the patterns and governance are identical, which is what prevents lock-in.

RAG & knowledge architecture

Four retrieval signals, fused without weights — grounded in 300–500 ms

Because “VM is down” embeds almost identically to “VM is up”. The fix is not a better embedding model — it is combining signal types.

Query
“GCP VM instance prod-api-01 in us-central1-a is unresponsive”
→
Query understanding
Intent: RESTART · entities · service · synonym expansion
→
Embedding
memory → Memorystore → disk → compute, then backfill all tiers
<1 ms cached
Four parallel retrieval agents — each with its own failure handling
Vector — semantic
✓ synonyms, paraphrase, intent
✗ negation, numbers, identifiers
Keyword — lexical
✓ error codes, exact terms
✗ no understanding of meaning
Graph — structural
✓ “what actually worked before?”
✗ cold start for new scripts
Metadata — explicit
✓ hard constraints: cloud, service, env
✗ limited to known fields
RRF fusion
Σ 1/(60+rank). No weights — only rankings
→
Cross-encoder rerank
Joint (query, doc) scoring — +20–30% precision
→
ACL + blast-radius filter
Filtered by the requesting principal in the query, then critical-risk candidates dropped
→
Top 5 + evidence
Match reasons, risk level, historical success count, avg resolution time
Why ranks beat scores
A vector score of 0.9 and a graph score of 0.9 do not mean the same thing. RRF only uses positions, so it is scale-invariant, needs no weight tuning, and stays stable when you add a retriever.

And it degrades gracefully: if one agent times out, a weighted average collapses — RRF loses only that agent's quarter of the contribution.
The knowledge graph answers what vectors cannot
Incident —FIXED_BY→ Script carries success, resolution time and human verification.
Service —DEPENDS_ON→ Service gives blast radius in one query — restarting Kubernetes surfaces api-gateway, payment-service, auth-service.
All “restart” scripts embed almost identically; only history can separate them.
↻ Learns from verified success — and un-learns on reopen
Success → FIXED_BY edge merged, resolved incident indexed, fusion weights retuned per incident type.
Failure → nothing is indexed. And if the incident reopens within 7 days the association is retracted — verification proves recovery at T+minutes, not T+3 days. A learning system without a retraction path only ever becomes more confident.
Five kinds of memory, no implicit memory
Working state (Memorystore, ~1 ms) · episodic (Cloud SQL, ~10 ms) · semantic (Vertex AI Search, ~50–100 ms) · relational (Neo4j, ~100–200 ms) · cache (<1 ms). Every LLM call receives explicit retrieved context — the model is never assumed to remember a prior turn, which is what makes runs reproducible and auditable.
⚠ If fewer than two agents respond
Return empty and escalate to a human. Do not guess.

Data engineering — APEX

Worked example: the nightly sales load fails at 02:14

Problem → agent analysis → tool / query → root cause → recommended action → result.

PROBLEM
Pipeline failed
sales_orders_daily fails at raw_to_bronze. Feed must land by 06:00. pipeline.failed published; on-call notified.
→
AGENT ANALYSIS
Intake & correlate
Fingerprint checked — not a duplicate. RCA classification run. Correlated against prior incidents on the same feed. Confidence and SLA deadline attached.
→
TOOL / QUERY
Metadata + execution log
Reads task_execution and error_log; compares the incoming DataFrame against schema_version; reads the feed's drift policy.
→
ROOT CAUSE
Schema drift under a STRICT policy
The source added two columns and retyped one. The feed's policy is STRICT — fail on any change. The job failed loudly with an explicit schema diff, exactly as designed.
→
ACTION
Two governed options
A. Register a new schema_version and move the feed to ADDITIVE.
B. Quarantine and continue for tonight, fix at source.
A schema change always requires human approval.
→
RESULT
Approved → metadata updated → re-run
No DAG code was edited. The pipeline is metadata-driven, so the new schema version changes runtime behaviour on the next run. Re-run is safe: raw_to_bronze deletes by _run_id before writing.

🔑 Secrets, data protection & retention
Secret Manager + Cloud KMS CMEK · 90-day automatic rotation · CI secret scanning, including on generated pipeline code · TLS 1.3 external, mTLS internal · PII masked before it reaches the model or the Gold zone · VPC Service Controls as a data-exfiltration perimeter · audit 7 years, PII 90 days.
🔐 MCP Gateway — the model never holds a credential
Agents ask for a named tool; the connector holds the credential and enforces its own authorisation. Tools are allowlisted per agent — the Terraform agent cannot call ServiceNow write tools. A prompt injection that convinces the model to “print all secrets” finds nothing to print. Every call traverses the MCP Gateway: one policy decision point evaluating agent × tool × parameters × environment, one audit choke point, fails closed.
🔑 ACL-aware retrieval
Retrieval is filtered by the requesting principal, inside the vector-store query — never post-filtered in application code. Chunks carry their source document ACL. Post-filtering is not access control: the content was still read, ranked and logged.
📜 Audit trail — every decision, every actor
Every AI decision recorded with explanation, confidence, risk level and a human-oversight flag. Every human decision recorded with the recommendation and the actual choice, including overrides and their stated reason. Checksummed, append-only, 7-year retention, queryable by incident ID.
⚖️ Enterprise governance posture
SOC 2 Type II — compliant ISO/IEC 42001 — compliant NIST AI RMF + GenAI Profile — aligned GDPR — compliant MITRE ATLAS — 7 techniques mapped EU AI Act high-risk — controls implemented; conformity assessment due 2 Dec 2027
20-control unified catalogue cross-mapped across all six frameworks — evidence gathered once serves every auditor. 12-entry AI risk register with named owners; the two highest residual risks are automation bias and provider behaviour drift — both people-and-process, not technical.
Article 14 requires meaningful oversight, not an approve button. Countermeasures: evidence-first payloads, explicit confidence and risk, auto-approval for genuinely routine actions to preserve attention, and approval dwell time measured as an automation-bias indicator.

📏 Maturity: Level 3 — Governed Autonomy
The AI acts autonomously inside a bounded, policy-defined envelope; humans approve everything outside it; every action is verified and audited.
The envelope itself is widened only by humans — the feedback loop tunes retrieval, never authority.
🚫 Level 5 is not the destination
Maturity models imply the top level is the goal. For a high-risk AI system, meaningful human oversight is a legal requirement, not a stage to outgrow. Level 3 with excellent verification and audit is the correct terminal state for this platform.
