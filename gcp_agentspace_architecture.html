The Two Tracks, One Machine

The platform runs two workflows on one architecture. The essential insight is that both tracks are the same machine: sense an event, route it, retrieve context, reason about it, validate the reasoning, obtain human authority, execute deterministically, verify the outcome, and learn.

Five Load-Bearing Ideas

1. The event log is the system of record

Every state change is an immutable Pub/Sub message. Any incident or pipeline can be replayed from a snapshot. Durability, decoupling and a compliance-grade audit trail in one mechanism.

2. A deterministic state machine controls the flow — the LLM never does

The Agentspace Agent Graph (LangGraph StateGraph in the portable stack) decides which node runs next. LLM nodes only reason; code nodes only execute. ReAct is explicitly forbidden.

3. Retrieval beats recall

A four-agent Swarm RAG system — vector, keyword, graph and metadata — searches in parallel, fuses with Reciprocal Rank Fusion (k=60), then reranks with a cross-encoder. No single retrieval method is trusted alone.

4. Two independent validators before every action

A Gemini-as-Judge on a different model scores quality, safety, factuality, feasibility and risk; then a human approves. High-risk and production changes always require a person.

5. The system only learns from success

Verified successful resolutions are indexed back into the vector store and graph. Failures are never indexed, so bad patterns cannot be reinforced.

⚠️ 2. Business Problem, Objectives & Scope

Two operational functions in every large enterprise consume disproportionate engineering effort while producing little differentiated value: IT incident response (triage alerts manually, search wikis for the right remediation, get approval over chat, run a script, write the ticket up by hand) and data pipeline development (hand-write an ingestion job, transformations, a validation suite, an orchestration DAG and a deployment — per feed, with slight undocumented variations). Both are pattern-heavy and judgement-light in the majority of cases, yet both are executed as bespoke, manual work.

The Challenge: Alert Fatigue & Manual Toil

Modern enterprises face an overwhelming volume of IT incidents and data pipeline requests. Traditional approaches suffer from several critical limitations:

❌ Current Pain Points

  • Alert Fatigue: Teams receive 1000s of alerts daily, 90%+ are noise
  • Slow Resolution: Average MTTR is hours to days for routine issues
  • Knowledge Silos: Remediation knowledge trapped in individual heads
  • Manual Pipelines: Data engineers spend 60% of time on boilerplate code
  • Inconsistent Quality: Pipeline code varies widely in style and security
  • Audit Gaps: Hard to track who did what and why
  • Scaling Issues: Can't hire fast enough to match infrastructure growth

✓ How We Solve It (Google Cloud)

  • AIOps via Cloud Operations: 94% noise reduction through intelligent deduplication
  • Agentspace Multi-Agent: Specialized agents find best remediation from knowledge base
  • Gemini Chain-of-Thought: Gemini 2.0 reasons through problems step-by-step
  • Template Generation: Jinja2 templates ensure consistent, secure code
  • Automated Validation: Built-in linting, schema checks, security scans
  • Pub/Sub Event Spine: Every action is an immutable, auditable event
  • Human-in-the-Loop: AI augments humans, doesn't replace judgment
⚠ Why generic AI assistants do not solve this

Off-the-shelf chat assistants and code copilots cannot enforce approval gates, cannot maintain a tamper-evident audit trail, cannot integrate as a first-class actor in ITSM workflows, and cannot guarantee output structure. Governance — not model quality — is the binding constraint in an enterprise. This platform exists to supply the governance layer around the model.

⚡ Why Google Agentspace + Gemini?

Google Agentspace provides enterprise-grade multi-agent orchestration with 100+ enterprise connectors and managed governance, giving the same deterministic agent-graph property as the portable LangGraph stack with less operational burden — the trade-off being vendor coupling. Combined with Gemini's large context window and native GCP integration, this delivers governed AI that fits into existing workflows while maintaining compliance.

🧱 6. Layered Architecture & Reference Models

The platform uses a strict layered architecture with unidirectional dependencies. A layer may call the layer below it; it may never call the layer above. This is what makes the audit trail complete and the blast radius of a change predictable.

Nine layers, one direction of dependency
L1 · Presentation
Next.js UI, dashboards, approval screens. Concern: human interaction. Must not: contain business logic or call agents directly.
L2 · API / Control Plane
FastAPI on Cloud Run, RBAC middleware, CQRS reads. Concern: authn/authz and request handling. Must not: poll external systems, call the agent graph directly, or execute workflows.
L3 · Orchestration
Agentspace Agent Graph, FAST Governor, 12-state phase machine. Concern: deterministic flow control. Must not: perform reasoning or execute infrastructure changes.
L4 · Agent / Domain
9 FAST agents, 5 APEX agents, business rules. Concern: what the system decides. Must not: control the loop — that is L3's job.
L5 · Intelligence
Swarm RAG, RRF, reranking, planner and judge models. Concern: inference and retrieval. Must not: take actions or hold credentials.
L6 · Integration
Tool servers / Agentspace connectors, A2A mesh, REST clients. Concern: talking to the outside world. Must not: leak external schemas upward.
L7 · Event / Messaging
Pub/Sub, schemas, dead letter topics. Concern: durable, ordered, replayable delivery. Must not: contain logic beyond routing and validation.
L8 · Persistence
Cloud SQL, Memorystore, vector store, Neo4j, Cloud Storage, BigQuery. Concern: state and storage. Must not: enforce business rules.
L9 · Infrastructure
GKE, VPC, IAM, Terraform, Secret Manager. Concern: where it all runs. Must not: be configured by hand.
⊕ Cross-cutting concerns — aspects, not layers
Observability · Security · Resilience · Governance · Cost. Applied via middleware, decorators and sidecars to every layer rather than sitting in the stack.
No upward calls — dependency direction checked in architectural and code review. No layer skipping for writes — all state changes traverse L7; verified by audit completeness. External schemas stop at L6 — the anti-corruption layer normalises to internal contracts. Credentials live at L6 and below — the model at L5 never receives a secret.

Status:      Accepted                      Date: 2025-01-15
Deciders:    Platform Eng, AI Eng          Supersedes: ADR-007

## Context
Four retrieval agents return scores on incompatible scales. The v4 design
combined them with hand-tuned weights (0.40/0.25/0.25/0.10). These weights
required re-tuning whenever an agent was added or its scoring changed, and a
failing agent collapsed the combined score.

## Decision
Adopt Reciprocal Rank Fusion with k=60, operating on rank positions rather
than raw scores.

+ No weight tuning; scale-invariant; robust to agent failure
+ New retrievers can be added without recalibration
- Loses the ability to express "this agent is genuinely more trustworthy"

- Team must understand a less intuitive formula

## Alternatives considered
- Keep weighted fusion: rejected, brittle
- Learned re-ranker: deferred, needs labelled data

Durable Execution — the Execution Ledger

⚠ The most safety-critical mechanism in the platform

Every other control protects against a wrong action. This one protects against a repeated action — which for a non-idempotent production change is often worse, because the first execution already succeeded and the second runs against a system that has already changed. No agent may cause an external side effect without an open ledger row.

at-most-once

💥 The dangerous window — and how it closes
A crash between steps 3 and 4 leaves the platform unable to distinguish “never dispatched” from “dispatched, acknowledgement lost”. On restart the Reconciler scans for rows in DISPATCHING and queries the external system by execution_id. Found and complete → adopt the result. Found and running → resume polling. Not found and idempotent → safe to dispatch. Not found and non-idempotent → ORPHANED, escalate to a human. Blind re-dispatch is forbidden.
Invariant 1: no external side effect without a committed ledger row. Invariant 2: dispatch carries execution_id as dedup key and tag. Invariant 3: open rows are reconciled, never re-dispatched. Invariant 4: executed artefact hash must equal approved artefact hash. Invariant 5: non_idempotent runbooks never auto-retry.

Reciprocal Rank Fusion — Why Ranks Beat Scores

RRF_Score(doc) = Σ ( 1 / (k + rankₓ) )

k       = 60   industry-standard constant
rankₓ  = position from agent i (1 = best)

Worked example, query "GCP VM down":

start_vm.sh    = 1/61 + 1/62 + 1/61 + 1/61 = 0.0653  ← winner
restart_vm.yml = 1/62 + 1/61 + 1/63 + 1/62 = 0.0645
reboot_server  = 1/63 + 1/63 + 1/62 + 1/64 = 0.0635

start_vm.sh wins because it ranks #1 with THREE agents,
even though restart_vm.yml ranks #1 on keyword alone.

  0.40·0.9 + 0.25·0.7 + 0.25·0.0 + 0.10·0.8 = 0.61  ← score collapses

Historical note on fixed weights

Version 4 of the platform used fixed weights (vector 0.40 / keyword 0.25 / graph 0.25 / metadata 0.10). Version 5 replaced this with RRF. Those weights survive only in the adaptive feedback optimiser, which tunes them per incident type from real outcomes rather than being hand-set globally. If you encounter 0.40/0.25/0.25/0.10 in older material, it is historical.

Access-Control-Aware Retrieval

⚠ Retrieval is filtered by the identity of the requester, not only by risk

Today the corpus is a first-party runbook registry where every operator may read every runbook, so the risk is latent. It stops being latent the moment any enterprise connector indexes Confluence, Drive, SharePoint or ticket history — an unfiltered index will retrieve a document the requesting user cannot open in its source system, and the model will summarise it back to them. The ACL was on the source system; the index has none.

RequirementImplementation
ACL propagation at ingestionEvery indexed chunk carries the source document access-control list as an indexed metadata field. Vertex AI Search supports document ACLs natively

No principal, no retrievalA retrieval without an authenticated principal is rejected. There is no “system” principal that bypasses filtering for user-facing queries
Agent-initiated retrievalWhen an agent retrieves on behalf of a workflow, the principal is the incident assignment group, not the platform service account
Classification filterRestricted / Regulated chunks are excluded from any retrieval summarised into a broader-audience channel
Test as a build gatetests/security/test_retrieval_acl.py must prove a low-privilege caller cannot retrieve a restricted document
Post-filtering is not access control

Retrieving 20 candidates and dropping the unauthorised ones in application code still means the unauthorised content was read, ranked, and may appear in logs, traces or a reranker input. The filter belongs in the query.

⚠ Memory is a security domain, not just a storage concern

Anything written to memory is read back later and influences a decision. A memory store without provenance and trust levels is an injection surface with a long delay between exploit and effect — which is exactly what makes memory poisoning hard to detect.

Four things that must never be conflated

Memory ≠ workflow state ≠ retrieval corpus ≠ conversation history. Four different lifecycles, four different access-control models, four different correctness requirements. Storing them together because they happen to fit in the same database is the most common way an agent platform becomes unmaintainable. Note in particular that workflow state and the execution ledger are not memory — they are state and durability records, and they belong in different stores with different guarantees.

Team preferences may only tighten automation, never loosen it

A team may declare “never auto-restart payment-service, even at LOW risk”. A preference must never become a privilege-escalation path. User memory is never indexed for semantic search and never enters a prompt as free text.

No implicit memory between LLM calls

Every call receives explicit, retrieved context. The model is never assumed to “remember” a prior turn. This is what makes runs reproducible and auditable — the same state produces the same prompt.

NOTHING is indexed. Indexing a failed remediation would make the system more confident about a solution that does not work — the failure mode is silent and compounding.
↻ Long-horizon feedback and retraction — the correction to the learning loop
Verification proves recovery at T+stabilisation-window. It says nothing about T+3 days. By the time an incident recurs, the learning engine has already recorded success. Without a long-horizon signal a remediation that masks a symptom rather than fixing a cause is positively reinforced, invisibly. A watcher correlates new incidents against closed ones by service + fingerprint class over 7 days; a match marks the resolution SUPERSEDED, retracts the FIXED_BY edge, decrements the success count and removes the resolved-incident document from the index. Reopened-rate SLO: <5% at T+7 days. Retraction is itself an event and an audit row. A learning system without a retraction path only ever becomes more confident — and confidence that cannot decrease is not learning.
⚠ Synthetic seed history is scaffolding, not evidence
Bootstrap history is generated with success probability assigned by risk level. Until real outcomes accumulate, the graph agent ranks on the assumptions of the seeding script. Every seeded record carries synthetic: true; synthetic outcomes are never cited to a human in match reasons or the approval payload, never counted toward the auto-approval historical-success precondition, and decay to zero weight once a script has ≥5 real verified outcomes. Where there is no real history the payload states “no verified history” — honest and actionable.
What is learned: disk incidents favour keyword matching (“no space left” is exact and distinctive); VM incidents are balanced; Kubernetes incidents favour semantic, because terminology varies widely across teams. This is learned from outcomes, not assumed.

Evidence-First Approval — What the Human Actually Sees

⚠ The autonomy policy, stated once

Auto-approval is available in non-production environments only. Every action targeting production requires a human approver — without exception, and regardless of risk tier, judge score or historical success rate. The environment condition is evaluated first and cannot be overridden by any confidence threshold or configuration value.

This is a deliberate starting position, not a permanent ceiling. Production auto-approval for a narrow runbook class is a future maturity capability requiring an ADR, a sustained reopened rate below SLO, 0% adversarial bypass and an instantly revocable feature flag. It is out of scope for the initial build.

The approval payload is not a yes/no prompt.

It contains everything needed to make a real decision:

📡 19. Protocol & Integration Architecture

The platform deliberately uses five distinct communication layers, each chosen for a property the others do not have. Choosing the wrong layer is how audit trails get holes in them.

Five communication layers
Layer 1 — Pub/Sub (Kafka in the portable stack)
External integration · state transitions · audit trail · replay. Guarantee: at-least-once, ordering per partition/key. Partition key = incident_id / pipeline_id. 7-day retention. Schema validation before publish.
Layer 2 — A2A (Agent-to-Agent)
Swarm consensus · judge evaluation · agent discovery. Guarantee: best-effort, real-time. Message types: swarm.query, swarm.vote, judge.evaluate, judge.score, agent.coordinate, agent.capability, agent.execute, agent.result.
Layer 3 — MCP / Agentspace connectors + Vertex Extensions
Agent-to-tool invocation. Guarantee: request-response with typed tool schemas. Discovery via tools/list — the agent needs no hard-coded knowledge. Credentials are held by the server, never by the agent or the model.
Layer 4 — REST / Webhooks
Cloud Build dispatch · Jira · chat · PagerDuty. Guarantee: request-response with retries.
Layer 5 — Direct SDK
Memorystore ~1 ms · Cloud SQL ~10 ms. No protocol overhead, no serialisation cost.

MCP versus A2A — They Solve Different Problems

MCP is agent-to-tool. A2A is agent-to-agent. Neither replaces the other.

Choosing the wrong one produces either a tool call pretending to be a conversation, or an agent conversation that should have been a typed function call.

Two historical CRITICAL gaps, and how they were closed

⚠ Development bypass

When ENVIRONMENT=local and AUTH_BYPASS=true, the middleware skips validation and grants admin to every request. A deployment that reaches staging or production with this set is an unauthenticated admin API on the internet. This must be asserted in a deployment smoke test, not left to discipline.

⚠ Holding the approver role is necessary, but never sufficient

Role-based authorisation answers “may this person approve things?” — not “may this person approve this thing, against this environment, with this blast radius?” Without the second question, an approver entitled only to staging can authorise a production change and the execution agent carries it out with full platform privilege. The audit log records a named approver, producing the appearance of accountability without the substance of authorisation. This is the classic confused-deputy problem and it is closed in code.

The action proceeds only if action_requirements ⊆ approver_entitlements. The platform's own service-account capability is a ceiling, never a grant.

Judge Input Isolation

⚠ The judge must not read attacker-controllable free text

The incident description is written by whoever raised the ticket — any employee, or any integrated monitoring system. If both the planner and the judge receive that raw text, a prompt injection that fools the planner may equally fool the judge. Using a different model family defends against shared model bias; it does not defend against shared poisoned input.

Raw incident description (free text)Yes — guardrailed, redacted, labelled untrusted_externalNoThe planner needs the narrative; the judge must not inherit its influence

The judge answers “does this plan follow from this evidence, and is it safe?” — not “does this plan match the narrative?”, which is the question an injection exploits. Output-side harmful-command detection is the real backstop: input guardrails are probabilistic, whereas a deterministic scan of the generated artefact is not. Weight engineering effort accordingly.

📖 34. Glossary

FAST
Federated Agents with Strict Transitions — the incident-track architecture: 9 specialised agents, 7 Governor phases and 12 workflow phase states.
APEX
The data-engineering agent, v2.1 — a metadata-driven pipeline compiler rather than an ETL tool. 9 DAG patterns, 5 canonical Spark jobs, 13 PostgreSQL DDL schemas.
Governor
The deterministic orchestrator above the agent graph. Sequences the 7 phases, holds the state machine, detects stalls, and escalates.
Swarm RAG
Four retrieval agents — Vector, Keyword, Graph, Metadata — searching in parallel and fused by RRF. Not to be confused with the cross-encoder reranker, which is a separate stage.
RRF
Reciprocal Rank Fusion. Combines rankings from multiple retrievers as Σ 1/(k + rank), k = 60. Scale-invariant, weight-free, extensible.
Cross-encoder reranking
Second-stage retrieval that scores (query, document) jointly rather than independently. +20–30% precision over bi-encoder ranking; final score = 0.70·rerank + 0.30·rrf.
Blast radius
The set of services affected if a change goes wrong, computed by breadth-first search over the Neo4j DEPENDS_ON graph. Feeds risk routing and filters critical-risk candidates out of retrieval.
FIXED_BY
The knowledge-graph edge from an Incident to the Script that resolved it, carrying success, resolution time and human-verification flags. This is how the platform remembers what actually worked.
Medallion architecture
Raw → Bronze → Silver → Gold → Trusted, with quality gates between Bronze→Silver and Silver→Gold. Failing records are quarantined, not passed through.
MCP
Model Context Protocol — the JSON-RPC 2.0 agent-to-tool standard used in the portable stack. Its GCP-native counterpart is Agentspace connectors plus Vertex AI Extensions. Its key property is that credentials live server-side, never in the model's context.
A2A
Agent-to-Agent messaging — real-time, best-effort coordination between agents (swarm voting, judge evaluation), as distinct from durable state transitions which always go through the event spine.
Shadow mode
A deployment mode in which plans are generated but never executed. Used both to validate a new model or prompt against production traffic, and as the platform's kill switch.
Evidence-first approval
An approval request that carries the reasoning, retrieved evidence, judge scores, blast radius, confidence and rollback availability — not just a yes/no prompt. Required for EU AI Act Article 14 meaningful oversight.
ReAct
The pattern in which the LLM itself drives the tool-use loop. Explicitly forbidden here — unpredictable and unauditable. A deterministic state graph controls flow instead.
VIGIL
The APEX self-healing pattern: 8 automatic remediation actions (retry, scale, repartition, reduce batch, skip corrupt, full reload, clear cache, quarantine and continue) guarded by a circuit breaker.
Grain verification
A join safety check: if a join multiplies row count by more than 2.0×, the task fails. A silent fanout is the single most common cause of wrong numbers reaching a dashboard.
Agentspace
Google Cloud's enterprise multi-agent platform with 100+ built-in connectors. Provides the managed agent-graph runtime in this variant; LangGraph fills the same role in the portable stack.
Chain-of-Thought (CoT)
AI reasoning pattern where Gemini thinks step-by-step before providing an answer, improving accuracy.
Cloud Composer
Google Cloud's managed Apache Airflow service for data pipeline orchestration and scheduling.
CQRS
Command Query Responsibility Segregation - writes go to Pub/Sub, reads come from Cloud SQL.
DLT (Dead Letter Topic)
Pub/Sub topic where failed messages are sent for later investigation and reprocessing.
Gemini
Google's most capable LLM family. Pro for complex reasoning, Flash for fast evaluation and judging.
Grounding
Gemini feature that verifies responses against trusted sources (Vertex AI Search, Google Search).
HITL (Human-in-the-Loop)
Design pattern requiring human approval before AI-generated actions are executed.
Pub/Sub
Google Cloud's serverless messaging service. Acts as the event spine and system of record.
Vertex AI Search
Google Cloud's enterprise search and RAG engine for grounded retrieval across enterprise data.
Vertex Extensions
Tool-use framework allowing Gemini agents to call external APIs, databases, and services.
