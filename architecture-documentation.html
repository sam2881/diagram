System Overview

This is an AI-powered autonomous incident management system that automatically detects, analyzes, remediates, and learns from infrastructure incidents. The system uses a hybrid protocol design to ensure reliability, auditability, and real-time performance.

Architecture Patterns

  • Hub & Spoke - Central orchestration
  • Hierarchical Agents - Layered decision making
  • Swarm (RAG) - Distributed knowledge retrieval
  • Event-Driven - Kafka-based state management

Design Patterns

  • ReAct - Reasoning + Acting loop
  • Chain-of-Thought - Step-by-step reasoning
  • Plan-Execute - Generate then execute plans
  • Self-Reflection - LLM validates LLM output

Communication Protocols

The system uses four distinct protocols, each optimized for specific communication patterns:

Kafka

External systems, audit trail, state transitions

A2A (Agent-to-Agent)

Real-time agent coordination

MCP (Model Context Protocol)

Agent-to-Tool invocation (JSON-RPC 2.0)

REST/Webhook

GitHub Actions, External APIs

Incident State Machine

Every incident flows through a defined state machine, ensuring traceability and compliance:

Happy Path

NEW → RECEIVED → ENRICHED → JUDGED → PLAN_GEN → APPROVED → EXECUTED → VERIFIED → CLOSED

Failure Path

FAILED → ROLLBACK → MANUAL

State Transitions via Kafka

All state transitions are published to Kafka topics for durability and audit compliance. This ensures that the system state can be reconstructed from the event log at any time.

Zone 1: Ingestion

Receive incidents from external sources, normalize them, reduce noise, and publish to the event bus.

1 ServiceNow (Incident Source)
External Webhooks

Sources: ServiceNow, GCP Alerts, Datadog, PagerDuty

  • An alert fires in the monitoring system
  • Incident contains: severity, affected service, description, timestamps
  • Multiple related alerts may fire simultaneously
2 SNOW MCP Server
MCP JSON-RPC 2.0
  • MCP Server receives the raw incident via JSON-RPC call
  • Transforms diverse alert formats into a unified schema
  • Passes to AIOps Correlator for deduplication

AIOps Correlator

  • Correlates related alerts (100 alerts → 1 incident)
  • ML-based noise filtering (-94% reduction)
  • Deduplication and event correlation

Protection Mechanisms

  • Idempotency: State hash check prevents duplicates
  • Circuit Breaker: 5 fails → 30s open
  • DLQ: Failed messages captured for review

Output: Kafka Topic incident.created

A single correlated incident is published to Kafka with: incident_id, severity, affected_systems, raw_data. ChatOps notifications sent to Slack/Teams/PagerDuty.

State Transition: NEW → RECEIVED

Zone 2: Intelligence

Enrich the incident with context, generate a remediation plan, assess risk, and validate with AI judge.

3 Event Orchestrator (Kafka Consumer)
Kafka Hub & Spoke Pattern
  • Consumes incident.created from Kafka
  • Acts as the central hub for the intelligence zone
  • Triggers the Decision Orchestrator
4 Decision Orchestrator (A2A Coordinator)
A2A Plan-Execute Pattern
  • Coordinates multiple AI agents via A2A protocol
  • Manages the workflow using LangGraph
  • Executes nodes: enrich → plan → risk → reflect

Swarm RAG

A2A (coordination) + MCP (tool calls)

  • Vector DB: Weaviate for embeddings
  • Graph DB: Neo4j for relationships
  • find_terraform() - Find relevant .tf files
  • find_ansible() - Find relevant playbooks
  • rank_scripts() - Rank by success rate
  • consensus() - Swarm voting

Memory Layer

Direct SDK (no protocol overhead)

  • Redis: ~1ms latency
  • Recent incidents, agent state, embeddings cache
  • PostgreSQL: ~10ms latency
  • Incident history, audit logs, configurations
5 LLM Reasoning
A2A Chain-of-Thought
  • LLM analyzes the enriched incident context
  • Generates step-by-step remediation plan
  • Calculates Risk Score (LOW/MEDIUM/HIGH)
  • Calculates Confidence Score (0-100%)
5b LLM-as-Judge
A2A Self-Reflection Pattern
  • A separate LLM instance evaluates the plan
  • Checks for: safety, completeness, blast radius, reversibility
  • Provides independent score (0-100%)
  • Can reject plans that are too risky

SLO/Error Budget

  • MTTR target: <30 minutes
  • Automation rate: >60%
  • Tracks performance against targets

Cost Controls

  • Token limit: 50K per incident
  • Cost ceiling: $5 per incident
  • Prevents runaway LLM costs

Deployment Modes

Shadow Plans generated but not executed (validation mode)
Canary 10% Only 10% of incidents auto-remediated
Production Full autonomous operation

Output: Kafka Topics

incident.enriched - Published when enrichment completes

plan.generated - Published when plan is ready for approval

State Transition: RECEIVED → ENRICHED → JUDGED → PLAN_GEN

Zone 3: Governance

Make approval decisions based on risk level, enforce human-in-the-loop for high-risk changes.

6 Control Plane (Hierarchical)
A2A Kafka
  • Receives the plan + risk score + judge score via A2A
  • Applies organizational policies
  • Routes based on risk level

Risk-Based Routing

Risk Level Action Example
LOW Auto-approve Restart a pod, clear cache
MEDIUM Async approval Scale deployment, update config
HIGH Manual approval required Database migration, infrastructure change

Human-in-the-Loop (P0 - Priority Zero)

For HIGH risk incidents, human approval is mandatory:

  • • Slack/Teams buttons - Approve/Reject with one click
  • • Escalation timer: 15min → reminder, 30min → manager, 60min → page on-call
  • • Override reason - Required for all manual decisions
  • • Audit trail - All decisions logged for compliance

Output: Kafka Topic incident.approved

State Transition: PLAN_GEN → APPROVED

Zone 4: Execution

Execute the approved remediation plan using infrastructure agents and CI/CD pipelines.

Critical Design Decision: No LLM in Execution

The Execution Orchestrator does NOT use any LLM. It only executes pre-approved, deterministic plans. This eliminates hallucination risk during actual infrastructure changes.

7 Execution Orchestrator (Hierarchical)
Kafka A2A No LLM
  • Consumes incident.approved from Kafka
  • Coordinates execution agents via A2A
  • Monitors Circuit Breakers (3 fails → 60s open)
  • Kill switch available for emergency stop
8 Terraform Agent
A2A MCP REST
  • Receives infrastructure task via A2A
  • Uses MCP to call K8s/Infra tools
  • Retrieves .tf files from Swarm RAG
  • Triggers GitHub Actions via REST
  • Runs: terraform plan → terraform apply
9 Ansible Agent
A2A MCP REST
  • Receives configuration task via A2A
  • Uses MCP to call Config tools
  • Retrieves .yml playbooks from Swarm RAG
  • Triggers GitHub Actions via REST
  • Runs the Ansible playbook
10 Code Agent
A2A MCP REST
  • Receives code fix task via A2A
  • Uses MCP to interact with GitHub
  • Creates Pull Request or Hotfix branch
  • Triggers CI/CD pipeline via REST

From Swarm RAG (MCP)

The execution agents receive remediation scripts from the Intelligence zone:

  • • Terraform .tf files
  • • Ansible .yml playbooks
  • • Kubernetes manifests

These are executed via GitHub Actions using workflow_dispatch REST API.

Rollback Mechanism

If verification fails, automatic rollback triggers:

  • • Terraform: terraform destroy or revert to previous state
  • • Ansible: Run rollback playbook
  • • State: FAILED → ROLLBACK → MANUAL

Output: Kafka Topics

incident.executed - Successful execution

exec.failed - Execution failed

DLQ - Dead letter queue for errors

State Transition: APPROVED → EXECUTED (or FAILED)

Zone 5: Feedback

Verify the fix worked, learn from outcomes, close tickets, and generate postmortems.

11 Verification
Kafka A2A
  • Consumes incident.executed from Kafka
  • Runs health checks on affected systems
  • Validates metrics returned to normal
  • Runs regression tests (no new issues)
  • LLM-as-Judge (via A2A) validates fix quality
12 Learning Engine
MCP NEVER on Failure
  • Only on SUCCESS, updates the Swarm RAG
  • Indexes the successful remediation script
  • Records: script_id, duration, confidence score
  • Boosts ranking score for scripts that worked
  • Future similar incidents will prefer this solution

Critical: Never Learn from Failures

The Learning Engine NEVER indexes failed remediation attempts. This prevents reinforcing bad patterns and ensures only proven solutions are recommended.

13 Ticket Closer
MCP
  • Uses MCP to call ServiceNow API
  • Updates incident: VERIFIED → CLOSED
  • Adds resolution notes and timeline
  • Links to postmortem document
14 Auto-Postmortem
REST
  • Timeline from OpenTelemetry traces
  • Root Cause Analysis by LLM
  • Jira ticket created via REST/Webhook
  • Includes Terraform audit log
  • Includes Ansible playbook log
  • Calibration feedback for LLM improvement

Output: Kafka Topics

incident.verified - Fix confirmed working

verification.failed - Fix did not work (triggers ROLLBACK)

incident.closed - Incident fully resolved

State Transition: EXECUTED → VERIFIED → CLOSED

Complete Flow Summary

End-to-End Incident Flow

1. INCIDENT OCCURS

└─→ ServiceNow/Datadog/PagerDuty alert fires

2. INGESTION

└─→ MCP Server normalizes → AIOps correlates (-94% noise)

└─→ Kafka incident.created

└─→ State: NEW → RECEIVED

3. INTELLIGENCE

└─→ Event Orchestrator consumes from Kafka

└─→ Decision Orchestrator coordinates agents A2A

└─→ Swarm RAG finds best remediation scripts

└─→ LLM generates plan (Chain-of-Thought)

└─→ LLM-as-Judge validates plan (Self-Reflection)

└─→ Kafka plan.generated

└─→ State: RECEIVED → ENRICHED → JUDGED → PLAN_GEN

4. GOVERNANCE

└─→ Control Plane evaluates risk

└─→ LOW: Auto-approve | MEDIUM: Async | HIGH: Human-in-the-Loop

└─→ Kafka incident.approved

└─→ State: PLAN_GEN → APPROVED

5. EXECUTION

└─→ Execution Orchestrator (NO LLM)

└─→ Terraform Agent → REST GitHub Actions → terraform apply

└─→ Ansible Agent → REST GitHub Actions → ansible-playbook

└─→ Code Agent → GitHub → PR/Hotfix

└─→ Kafka incident.executed

└─→ State: APPROVED → EXECUTED

6. FEEDBACK

└─→ Verification (health + metrics + regression)

└─→ Judge validates fix quality A2A

└─→ Learning Engine updates RAG MCP (SUCCESS ONLY)

└─→ Ticket Closer updates ServiceNow MCP

└─→ Auto-Postmortem creates Jira REST

└─→ Kafka incident.closed

└─→ State: EXECUTED → VERIFIED → CLOSED

7. FAILURE PATH

└─→ If verification fails: FAILED → ROLLBACK → MANUAL

└─→ Automatic rollback triggered

└─→ Human intervention required

Key Design Decisions

Decision Rationale
No LLM in Execution Deterministic execution eliminates hallucination risk during infrastructure changes
LLM-as-Judge Independent validation by a separate LLM prevents bad plans from being approved
Swarm RAG Multiple agents reaching consensus produces better remediation recommendations
Never learn from failures Prevents reinforcing bad patterns; only proven solutions are indexed
Human-in-the-Loop for HIGH risk Critical changes require explicit human approval for safety
Circuit Breakers everywhere Prevents cascade failures; automatic isolation of failing components
Kafka for state transitions Provides durable audit trail, replay capability, and compliance evidence
A2A for real-time coordination Low-latency agent communication for time-sensitive decisions
MCP for tool invocation Standardized JSON-RPC 2.0 protocol for all agent-to-tool communication
REST for external APIs Standard HTTP/webhook integration with GitHub Actions, Jira, etc.
